## 2. 后端审核（`scripts/server/`）

### 2.1 【P0-1】上传记录的 `stored_path` 为空时，下载接口会让整个 Node 进程崩溃

**位置**：`scripts/server/api.mjs:339`（写入）、`scripts/server/api.mjs:359`（读取）、`scripts/server/db.mjs`（`uploadPath`）

`createScore` 分两步写：

```js
// api.mjs:318  INSERT 时 stored_path 先写死成空串
`INSERT INTO scores (..., stored_path, created_at) VALUES (..., '', ?)`
...
// api.mjs:339  文件写成功后才回填
ctx.db.prepare('UPDATE scores SET stored_path = ? WHERE id = ?').run(relPath, id)
```

而 `getScoreFile` 用这个字段拼路径：

```js
// api.mjs:355
const abs = uploadPath(ctx.dataDir, row.stored_path)   // stored_path === '' 时 === dataDir
if (!fs.existsSync(abs)) throw fail(404, '文件丢了')     // dataDir 存在 → 不报错
const stat = fs.statSync(abs)                          // 是目录, size = 目录项大小
res.writeHead(200, { 'Content-Length': stat.size })
fs.createReadStream(abs).pipe(res)                     // 没有 error 监听 → EISDIR
```

**为什么是崩溃而不是 404**：`path.join(dataDir, '')` 恰好等于 `dataDir`（已实测：`uploadPath(dataDir,'') === dataDir` → `true`）。`fs.createReadStream(目录)` 会抛 `EISDIR`，而 `pipe()` **不会**把源流的 `error` 事件转交给目标，也不会给源流挂监听 → Node 抛未捕获异常 → 进程退出。

**已用最小复现验证**：

```
>>> UNCAUGHT EXCEPTION: EISDIR - EISDIR: illegal operation on a directory, read
node exit code: 7
```

**触发条件**：`stored_path` 停在 `''` 需要 INSERT 成功而 UPDATE 失败/未执行。窗口本身只有几毫秒，但**不是理论问题**：
- SQLite 在 `SQLITE_BUSY`（库被锁）时 UPDATE 会抛错——而当前代码**没有 try/catch 包住这个 UPDATE**，异常会冒到 `handleApi` 的 catch 里返回 500，**行留在库里且 `stored_path` 永远是 `''`**。
- 进程在这个窗口被 `SIGKILL` / 断电，同样留下永久性的坏行。

一旦库里存在这样一行，**任何登录用户访问 `GET /api/scores/:id/file` 就能让公网服务进程退出**，且重启后该行仍在 → 变成**可重复触发的持久 DoS**。

**修法（建议按顺序做）**：

1. **加护栏**（5 行改动，立刻止血）：
   ```js
   if (!row.stored_path) throw fail(404, '文件还没落盘')
   ```
   同时给 `fs.createReadStream(abs)` 加 `.on('error', ...)` → 500 而不是崩溃。
2. **改成"先落盘再入库"**：把文件写到临时路径 → `fs.renameSync` 到最终路径 → **一次 INSERT** 写全 `stored_path`。这样根本不存在中间态。
3. **给 UPDATE 包 try/catch**：失败时 `DELETE` 掉那一行（跟 `writeFileSync` 的处理保持一致）。
4. **加一条启动自检**：`SELECT id FROM scores WHERE stored_path = ''` → 有则清理掉。

### 2.2 【P0-2】同步 scrypt 阻塞事件循环，单次登录即可让服务不可用

**位置**：`scripts/server/auth.mjs:25`（`hashPassword`）、`scripts/server/auth.mjs:49`（`verifyPassword`）

```js
export function hashPassword(password) {
  const hash = crypto.scryptSync(password, salt, KEY_LEN, { N: 16384, r: 8, p: 1 })
```

`scryptSync(N=16384, r=8)` 需要 **16 MB 内存 + 几十到上百毫秒纯 CPU**。Node 是单线程的，这段时间里**事件循环完全停摆**——静态资源、LED 代理（`/led-proxy`）、所有 API 全部排队。

影响面比看上去大：这个后端同时承担三件事——① 静态站点 ② 用户系统 API ③ WSS 反向代理（`scripts/serve-dist.mjs:104`，LED 灯带的控制通道）。**一次登录就能把灯带控制和网页一起卡住**。

再叠加 §2.3 的限流绕过，攻击者可以低成本地持续触发。

**修法**：

- 首选：改成异步 `crypto.scrypt(password, salt, keylen, opts, cb)`（或 `promisify`），`await` 之。Node 的 scrypt 异步版走的是 **线程池**，不阻塞主线程。
- 若担心线程池被占满：限制线程池大小 + 保留现有的 IP 限流作为兜底。
- 不建议为了"省时间"降低 `N`——`N=16384` 已经是偏低的现代取值。

### 2.3 【P1-1】IP 限流可被 `X-Forwarded-For` 伪造，限流形同虚设

**位置**：`scripts/server/api.mjs:62-66`

```js
function clientIp(req) {
  const xff = req.headers['x-forwarded-for']
  if (typeof xff === 'string' && xff.length > 0) return xff.split(',')[0].trim()
  return req.socket.remoteAddress ?? 'unknown'
}
```

取的是 **第一个** 段。nginx 默认的 `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` 是**追加**语义：客户端自带的 `X-Forwarded-For: 1.2.3.4` 会被放在**最前面**，真正的客户端 IP 排在后面。

于是攻击者只要每个请求换一个 `X-Forwarded-For`：

```
X-Forwarded-For: 10.0.0.1
X-Forwarded-For: 10.0.0.2
...
```

就能让 `REGISTER_LIMIT`（20 次/小时）和 `LOGIN_LIMIT`（20 次/10 分钟）**完全失效**，无限次撞库 + 无限次触发 §2.2 的同步 scrypt。

**修法**（二选一，取决于 nginx 侧怎么配）：

- **推荐**：nginx 侧改成 `proxy_set_header X-Forwarded-For $remote_addr;`（**覆盖**而非追加），此时后端取 `xff.split(',')[0]` 即为真 IP。但要注意 frps/frpc 链路会加一层，需确认最终到这里的头是否被覆盖。
- **后端兜底**：只信任**最后一段**（`xff.split(',').at(-1)`），前提是反代是覆盖语义。
- **更稳**：引入 `TRUSTED_PROXY_HOPS` 配置，明确"从右往左跳过 N 跳后剩下的第一段才是客户端 IP"，nginx 侧同时用覆盖语义。两边都配才稳。

**顺带**：`isSecure()`（`api.mjs:70-78`）也依赖 `x-forwarded-proto` / `x-original-proto`。伪造这两个头只能让 cookie 多一个 `Secure`（更安全方向），**不构成漏洞**，但同样应该收敛信任模型。

### 2.4 【P1-2】上传接口无配额、无速率限制，可写满磁盘 / 撑爆内存

**位置**：`scripts/server/api.mjs:32`、`:302`

```js
const MAX_FILE_BYTES = 50 * 1024 * 1024   // 50MB
...
const buf = await readBody(req, MAX_FILE_BYTES)   // 全量进内存
```

限流只覆盖了 register / login 两个端点（§2.3），`POST /api/scores` **完全裸奔**：

- **磁盘**：任意一个登录账号可以连续上传 50MB 文件直到磁盘写满。代码注释写着"用户选了不限额上传"，但"不限额"和"不设防"是两回事——需要一个**防滥用**的底线（而不是商业配额）。
- **内存**：`readBody`（`api.mjs:99-107`）把整个 body 收进 `chunks[]` 再 `Buffer.concat` → **单次上传峰值占用 50MB（+ concat 时的第二份拷贝 ≈ 100MB）**。10 个并发上传 ≈ 1 GB。这与文件头注释里"不是配额，是防 OOM"的意图相反。
- **文件描述符 / 连接**：无并发上限。

**修法**：

1. **流式落盘**：`req.pipe(fs.createWriteStream(tmpPath))`，边收边写，内存占用恒定；同时在流上做字节计数，超限直接 destroy。这是最有价值的一条。
2. **按用户配额**：DB 里 `SUM(size) WHERE user_id = ?`，超过阈值（如 1 GB）拒绝。
3. **上传速率限制**：复用现有的 `allowAttempt()`，给 `/api/scores` 加一条（如 30 次/小时/用户）。
4. **全局并发上限**：用一个信号量限制同时进行的上传数。

### 2.5 【P1-3】`verifyPassword` 直接采用数据库里的 `N/r/p`，无边界检查

**位置**：`scripts/server/auth.mjs:33-62`

```js
const [, n, r, p, saltB64, hashB64] = parts
actual = crypto.scryptSync(password, salt, expected.length, { N: Number(n), r: Number(r), p: Number(p) })
```

`N/r/p` 来自数据库里的哈希串。正常流程下它们是本服务自己写进去的，**但**如果数据库被篡改（备份被改、误操作、未来的 SQL 注入），`N` 就能被设成 `2^30` → scrypt 申请巨量内存 → 进程 OOM。

**修法**：解析后校验 `N === 16384 && r === 8 && p === 1`（或至少 `N <= 1e6 && r <= 32 && p <= 16`），不匹配直接 `return false`。顺带把 `expected.length` 也限制在 `[16, 128]`。

### 2.6 【P1-4】非法百分号编码的 URL 会返回 500 而不是 400

**位置**：`scripts/server/handler.mjs:40`

```js
const decoded = decodeURIComponent(urlPath.split('?')[0])
```

`decodeURIComponent('%ZZ')` 抛 `URIError`。这个异常在 `serveStatic` 里抛出 → 被 `handler` 的 catch 吞掉 → **返回 500 并打一条 error 日志**。

正确行为是 **400 Bad Request**。同理，`%00` 解码出 NUL 后虽然路径检查会拦住，但报错也不对。

**修法**：

```js
let decoded
try { decoded = decodeURIComponent(urlPath.split('?')[0]) } catch { return null /* → 400 */ }
```

> 顺带：目录穿越防护本身是**正确的**——`path.resolve` + `startsWith(root + path.sep)` 的写法能挡住 `../` 和 `%2e%2e%2f`（只解码一次，不存在双重解码问题）。这部分不用动。

### 2.7 【P1-5】静态资源缓存策略对"非 hash 文件"是错的

**位置**：`scripts/server/handler.mjs:75`

```js
'Cache-Control': file.endsWith('index.html') ? 'no-cache' : 'public, max-age=3600'
```

一刀切给 1 小时。但 `public/` 下的文件**没有内容 hash**（Vite 只给 `assets/` 下的产物加 hash）：

- `/library/manifest.json` —— 前端 60s TTL 缓存它（`src/library.ts:39`），而服务端给 1 小时 → **改 manifest 后要等 1 小时才生效**，这正是当初写 TTL 想解决的问题，但被服务端的缓存又覆盖了一层。
- `/library/**.mid` —— 同理，改曲库文件 1 小时内不生效。

**修法**：

```js
const rel = path.relative(root, file).replace(/\\/g, '/')
const cache = rel.startsWith('assets/')
  ? 'public, max-age=31536000, immutable'   // vite 产物带 hash
  : rel.endsWith('.html') ? 'no-cache'
  : 'no-cache'                                // manifest.json / library/*.mid
```

### 3.1 【P1-7】`parseUrl` 不检查 HTTP 状态码 → 私有谱子报错信息完全误导

**位置**：`src/parser/index.ts:27-42`

```js
export async function parseUrl(url: string): Promise<Song> {
  const resp = await fetch(url)          // ← 没有 resp.ok 检查
  if (lower.endsWith('.mid') || ...) {
    const buf = await resp.arrayBuffer()
    return parseMidi(new Uint8Array(buf))
  }
```

私有谱子走 `/api/scores/:id/file`（`src/library.ts:117`）。**session 过期**时服务端返回 `401` + `{"error":"请先登录"}` → 这里不检查 `resp.ok` → 把这段 JSON 当成 MIDI 字节 → `parseMidi` 抛 `MIDI 解析失败` 之类的底层错误。

用户看到的是"文件坏了"，实际是"请重新登录"。**这是会直接导致用户重复操作（重新上传文件）的错误提示。**

**修法**：

```js
if (!resp.ok) {
  let msg = `加载失败 (${resp.status})`
  try { const j = await resp.json(); if (j?.error) msg = j.error } catch {}
  throw new Error(msg)
}
```

> 公共曲库路径（`loadManifest`）已经正确检查了 `resp.ok`（`src/library.ts:52`），只有 `parseUrl` 漏了。

### 3.2 【P1-8】生产构建把整个 store 挂到 `window.__store`

### 3.5 【P2-10】单一 zustand store 承载全部 UI 状态

`src/store.ts` 有 **60+ 字段/动作**，其中 **25 个是 LED 相关**。问题：

- LED 建连 effect（`src/App.tsx:410` 起）的依赖是 `[ledEnabled, ledHost, ledToken, ledBackend, ledDualStrip, bus, ...]` → **这 5 个配置项任意一个变化都会 `teardown(false)` → 断开重连灯带**。改 host / token / 后端 / 单双色带都确实需要重连（`init` 的 count 不同），所以这个设计本身合理；但它意味着**把这 5 项从主 store 拆出去**的收益比看起来更大——拆分后可以把重连触发条件收窄到真正需要的字段。
- （`ledUpperBrightnessRatio` 和 `ledUpperNoteCount` 走的是各自的独立 effect，**不会**触发重连——这点没问题。）
- `setCurrentTime` 每 100ms 触发一次 → 所有订阅 `currentTime` 的组件重渲染（目前只有 `Transport`，可接受）。

**建议**：拆成三个 store：

- `usePracticeStore` —— song / hand / score / 当前时间（高频）
- `useLedStore` —— 全部 LED 配置（低频）
- `usePrefsStore` —— localStorage 持久化层

这样改 LED 配置不会触发练习态的重渲染，也让"哪些字段要持久化"一目了然。

### 3.6 【P2-11】上灯带提示：查询本身没问题，但索引重建时机不对

**先说结论**：这条**不是**性能瓶颈。我最初怀疑的两处 O(n) 扫描，核查后确认**都不成立**：

- ✅ `NextNoteIndex.at()` 用的是**二分查找**（`src/led/dualStrip.ts` 的 `findNext`），不是线性扫描。
- ✅ LED 预扫描器 `LedScanCursor.advance()` 用**双指针增量推进**（`onPtr` / `offPtr`，`src/led/scanCursor.ts:254`），每帧摊还 O(1)，不是全表扫描。
- ✅ `LedController.setUpperHints` 内部有 `sameHints` 去重，内容没变就不发包。

**真正存在的是两个小问题**：

1. **改"上灯带显示几个音"会重排整首曲子**。`src/App.tsx:745` 在 effect 体内 `new NextNoteIndex(song, ...)`，而该 effect 的依赖数组含 `ledUpperNoteCount` → 构造函数里的 `[...song.notes].sort((a,b) => a.time - b.time)` 会**整首复制 + 重排**。但索引内容跟 `count` 无关（`count` 只在查询时用）。
   **建议**：把构造用 `useMemo(() => new NextNoteIndex(song, split), [song, split])` 固定，`count` 作为查询参数传进去。
2. **每 50ms 重建一次 `hints` 数组**（`src/App.tsx:760`）→ 每秒 20 次数组 + `LedHint` 对象分配。量不大，但因为有 `sameHints` 去重，**实际不影响发包量**，属于可忽略的 GC 压力。
   **建议**：若要省，可以把轮询周期放宽到 100ms（上灯带是"接下来弹什么"的提示，100ms 人眼分辨不出），或复用同一个数组原地改写。

### 3.7 【P2-12】`Player.stepLoop` 每帧做若干次无谓的 store 往返

**位置**：`src/engine/Player.ts:637-660`

```js

this.clock.setLatencyCompensation(...)             // 每帧调
```

**建议**：把 `setSpeed` / `setLatencyCompensation` 改成"值变化时才调"（在 `useEffect` 里同步 store → clock，而不是在每帧的 `stepLoop` 里）。

## 4. 工程质量

### 4.1 【P3】没有 lint / format / CI

现状：

4. **`noUnusedLocals` 打开**——先跑一遍看看存量有多少，量大的话分两步走。

### 8.6 顺手修的一个真 bug

`src/engine/Accompaniment.ts` 的 `outputId` 字段（用户选中的输出端口 id）原本**只写不读** ——
注释和测试都写着「断连后仍保留用户的 id，便于自动重连」，但 `refresh()` 里根本没实现重连，
设备拔掉再插回来，用户必须重新选一次。

本轮在 `refresh()` 里补上了自动重绑：设备重新出现且 `state === 'connected'` 时，
自动用记住的 `outputId` 重新绑定并恢复连接状态（`setConnected(true)` + `resetDeviceState()`）。
只在 `onstatechange` 触发的 `refresh()` 这条路径上生效 —— `send()` 失败导致的 `handleDisconnect()`
不经过这里，避免端口真死了还反复重绑造成抖动。
